# Adversarial Friends 0.3.0 Release Design

**Date:** 2026-09-01

**Status:** Approved for implementation

## Context

`main` at `ee4bf96cb51ff298d33b1b09fc0041ab094c95fa` contains the completed
activation, Codex host-friend, provider-scoped authority, generic harness,
and Antigravity work intended for the next public release. The repository is
still versioned as 0.2.1 and is 21 commits ahead of `origin/main`. A separate,
synchronized OpenCode adapter fix adds `GOOGLE_GENERATIVE_AI_API_KEY` to the
provider's explicit environment allowlist because OpenCode's Google provider
reads that variable even though `opencode auth list` advertises
`GEMINI_API_KEY`.

The release must make the repository, packaged skill, plugin mirror,
architecture diagrams, public documentation, PyPI distribution, GitHub
release, and local Codex installation tell one consistent 0.3.0 story. It
must also preserve historical design and review records as history rather
than rewriting them to look current.

## Goals

- Release exactly the approved `ee4bf96` feature set plus the synchronized
  OpenCode credential fix as version 0.3.0.
- Remove or update stale statements in live documentation, examples,
  manifests, badges, evals, and generated diagrams.
- Preserve deliberately historical specs, plans, and review records when
  they are clearly labeled as historical.
- Prove that every committed diagram is regenerated from, and semantically
  agrees with, its PlantUML source and the current runtime contract.
- Verify source, wheel, sdist, isolated install, CLI version, plugin mirror,
  and release notes before publication.
- Publish through the existing trusted-publishing workflow, then verify PyPI
  and GitHub from their authoritative public endpoints.
- Refresh the local CLI and Codex plugin from the released contents and
  verify the installed provenance.

## Non-goals

- Unrelated changes arriving after the release boundary do not enter 0.3.0;
  they wait for 0.3.1 unless they are required to make 0.3.0 correct.
- Historical specs, plans, code reviews, and their old version/path examples
  are not mass-rewritten or deleted merely because they describe an earlier
  state.
- This release does not claim that Antigravity prevents all provider tools.
  It remains deny-by-default and requires the explicit scoped fallback
  documented in the already-approved feature design.
- The release does not change the trusted-publishing architecture unless an
  actual verification failure proves that a repair is required.
- The release does not introduce RepoGerbil or another changelog generator.

## 1. Frozen release boundary and isolation

Release work occurs on `codex/release-0.3.0` in a dedicated worktree created
from `ee4bf96`. The baseline must pass before release edits begin. The two
OpenCode adapter copies currently changed in the primary checkout are copied
into the release branch as an intentional, reviewed change; the primary
checkout's uncommitted files are not modified or discarded.

Before integration, compare `main`, `origin/main`, and the release branch.
If another actor moved `main`, classify each new commit explicitly:

- required for the release's correctness: reconcile and verify it;
- unrelated or incomplete: leave it for 0.3.1;
- conflicting with the frozen release: stop publication and resolve the
  conflict rather than silently choosing one side.

The release commit must be an ancestor of pushed `origin/main` before the
`v0.3.0` tag is pushed. This matches the enforcement already present in the
release workflow.

## 2. OpenCode credential repair

The canonical adapter at
`src/adversarial_friends/assets/adapters/opencode.toml` adds
`GOOGLE_GENERATIVE_AI_API_KEY` to `env.pass`. The explanation stays beside
the entry so future maintainers understand why both Google variable names
are retained. The plugin copy is produced through the repository's mirror
sync workflow and must remain byte-identical to the canonical asset.

A focused regression test must prove all of the following:

- the canonical OpenCode adapter passes `GOOGLE_GENERATIVE_AI_API_KEY`;
- it continues passing `GEMINI_API_KEY` for compatibility;
- unrelated environment variables remain denied by default;
- the packaged and plugin-mirrored adapters remain synchronized.

The fix changes only the explicit credential allowlist. It does not widen
external-tool authority or filesystem confinement.

## 3. Definition of stale content

The audit distinguishes live truth from historical evidence.

### Live surfaces

These must describe 0.3.0 behavior and metadata accurately:

- top-level `README.md`, `AGENTS.md`, `CONTRIBUTING.md`, and live pages linked
  from `docs/README.md`;
- canonical `SKILL.md`, adapter files, lenses, references, examples, and eval
  fixtures that instruct current users or test current behavior;
- plugin and marketplace manifests, package metadata, `VERSION`, badges, and
  install commands;
- GitHub workflows and release-facing scripts;
- PlantUML sources and committed PNG/SVG renders;
- the current 0.3.0 release section of `CHANGELOG.md`.

A live statement is stale when it contradicts the code, uses an obsolete
command or flag as current guidance, reports a wrong default/count/version,
links to a missing current file, or shows a generated visual that no longer
matches its source.

### Historical surfaces

Files under `docs/superpowers/specs`, `docs/superpowers/plans`, and completed
review records may retain old versions, paths, counts, decisions, and command
examples when the documentation index or the file itself makes their
historical status clear. The audit may add a concise historical notice where
that status is ambiguous, but it must not rewrite the historical record to
pretend an old plan described 0.3.0.

Search results are therefore classified, not blindly replaced. Every
remaining 0.2.x reference must be either an intentional compatibility/history
reference or a documented release artifact.

## 4. Documentation contract

Current documentation must agree on the following user-visible behavior:

- conversational activation accepts `afriend ...` and `afriend to ...`, but
  generic review requests do not implicitly activate the skill;
- in Codex, Codex orchestrates and is also included as a host self-reviewing
  friend by default, with `--exclude-self` as the opt-out;
- host self-review is advisory and cannot satisfy independent judging or gate
  quorum;
- default mode is `report`; judging blocks use three total rounds; loop mode
  allows five iterations unless the user overrides it;
- external-tool access is denied by default and
  `--allow-external-tools=<provider>` grants only named providers; only `*`
  is global;
- Antigravity uses the generic staged harness but remains uncontrolled in
  0.3.0, so it requires `--allow-external-tools=agy`;
- providers can be enabled or disabled through documented roster/configuration
  mechanisms, and automatic selection never overrides explicit exclusions;
- all shipped modes and their exit behavior match the CLI and reference docs;
- `GOOGLE_GENERATIVE_AI_API_KEY` is an allowed OpenCode credential variable
  where environment-variable guidance is enumerated.

Examples must be executable or intentionally schematic and labeled as such.
Links in current docs must resolve within the repository or to the intended
public endpoint. The README test badge/count is updated only if the final test
count changes.

## 5. Architecture diagrams

Every `docs/architecture/*.puml` file is reviewed against the implementation,
especially the run flow, host self-review, scoped provider authority, staged
workspace assets, report-versus-judging behavior, resume checks, and claim
lifecycle. Source changes are made only when the current diagram is
semantically stale.

Run `make diagrams` to regenerate all committed PNG and SVG files. A second
generation from the same source must leave the worktree unchanged. The audit
also verifies that every source has the expected committed renders and that
no orphan render remains after a source is removed or renamed.

## 6. Version and release notes

`VERSION` and every plugin manifest version become exactly `0.3.0`. Package
metadata continues deriving its version through the existing mechanism; no
second package-version source is introduced.

`CHANGELOG.md` gains a `## 0.3.0` section suitable for both PyPI-era users and
the GitHub release. It summarizes user-visible outcomes rather than commit
mechanics:

- narrow `afriend` conversational activation;
- Codex's default dual orchestrator/friend role and honest advisory labeling;
- provider-scoped, deny-default external-tool grants;
- generic digest-pinned harness staging and Antigravity's explicit fallback;
- the OpenCode Google credential fix;
- documentation, diagram, audit, and packaging hardening included in the
  release.

Release notes must not overclaim provider independence, Antigravity tool
denial, or an automatically recurring review loop.

## 7. Verification ladder

Verification proceeds from narrow and cheap to broad and release-equivalent:

1. Red-green regression coverage for the OpenCode allowlist.
2. Focused documentation, adapter, manifest, release-workflow, and diagram
   tests.
3. Canonical-to-plugin mirror sync and version sync.
4. `make diagrams`, followed by a clean second regeneration.
5. Complete `make quality`, including the full portable suite, wheel build,
   package-data checks, and isolated install.
6. An explicit fresh wheel and sdist build with exactly two distributions,
   `twine check --strict`, installation into a fresh temporary environment,
   and `afriend --version` equal to `afriend 0.3.0`.
7. A final diff review against the frozen boundary and an adversarial code
   review before integration.

Linux-only bubblewrap assertions remain CI evidence because macOS cannot
reproduce them locally. All portable gates must pass locally before push.

## 8. Publication and recovery

Publication order is strict:

1. integrate the reviewed release branch into local `main` without losing
   concurrent work;
2. rerun a proportional post-integration verification on `main`;
3. push `main` and verify the remote commit;
4. create `v0.3.0` at that exact commit and push the tag;
5. monitor the `Release` workflow through build, PyPI trusted publishing, and
   GitHub release creation;
6. verify PyPI's project JSON and the GitHub release/tag/assets independently.

Do not move or recreate a pushed tag to conceal a failure. A transient failure
before PyPI publication may be rerun against the same tag. If correcting the
failure requires a source or workflow change after the tag exists, repair
forward on `main` and use the next version rather than moving `v0.3.0`. If
PyPI already contains 0.3.0, its immutable files define the published release;
any corrective code requires a later version. The GitHub release job is
deliberately repairable and may update notes/assets for the same immutable
tag.

## 9. Local Codex refresh

After public verification, install `adversarial-friends==0.3.0` from PyPI and
confirm `afriend --version`. Refresh the personal Codex plugin using the
repository's cachebuster and reinstall flow, then verify that the cached
manifest and skill contents are derived from the 0.3.0 release commit and
that the skill description still exposes the narrow `afriend` activation.

The source version, published package version, plugin manifest version,
cachebuster-qualified installed plugin version, and Git commit are recorded
separately so the cache suffix is not mistaken for the package version.

## Acceptance criteria

The release is complete only when:

1. The approved OpenCode fix is tested and present in both synchronized
   adapter copies.
2. All live docs and examples accurately describe 0.3.0, while historical
   records remain explicitly historical and intact.
3. Every architecture diagram matches current semantics, all renders are
   regenerated, and regeneration is reproducible.
4. `VERSION`, plugin manifests, package distributions, isolated CLI, and
   changelog section all say 0.3.0.
5. All portable quality gates and the release-equivalent distribution checks
   pass from the final release commit.
6. The release commit is pushed to `origin/main` before `v0.3.0` is pushed.
7. The trusted-publishing workflow succeeds and authoritative PyPI and GitHub
   endpoints expose version 0.3.0 with the expected artifacts.
8. The local CLI and Codex plugin are refreshed and their installed versions
   and provenance are verified.
