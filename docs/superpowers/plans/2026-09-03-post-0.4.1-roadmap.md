# Post-0.4.1 Product Roadmap Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> `superpowers:subagent-driven-development` (recommended) or
> `superpowers:executing-plans` to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a review artifact live independently of the repository whose
code friends inspect, then add deliberate preflight, bounded failure handling,
and lower-friction installation in separate releases.

**Architecture:** The first release adds an explicit repository authority to
`afriend run`: the artifact remains frozen in the run directory while the
separately named Git root is snapshotted for repo-scoped friends. That is a
security boundary, not a convenience shortcut, so the run metadata must say
whether the artifact is Git-blob-bound to the snapshot. The remaining three
workstreams are deliberately independent; each starts with its own approved
design before implementation.

**Tech Stack:** Python 3.11+ stdlib, `argparse`, Git CLI, TOML adapter data,
pytest, Ruff, mypy strict, PlantUML, GitHub Actions, PyPI trusted publishing.

---

## Program boundary and ordering

Implement and release these workstreams independently:

1. **Explicit code context (`--repo`)** — implement next. It completes open
   issue #3 and removes the artifact-location trap without changing default
   behavior.
2. **No-dispatch preflight** — design only after `--repo` is released. It
   presents the actual scope, roster, authority, and resource caps before any
   friend is launched.
3. **Classified failure and retry policy** — design only after preflight. It
   must not add a generic provider probe that can charge money, authenticate,
   mutate state, or invoke a model.
4. **Distribution refresh UX** — design only after the other workstreams. It
   makes a released plugin payload straightforward to refresh in Codex and
   Claude without claiming that a package release auto-updates either host.

Do not bundle the later workstreams into the `--repo` release. Close issue #2
separately: its resolver bug is fixed and covered by 0.4.1.

## Workstream 1: explicit repository context

### Product contract

Add this invocation:

```console
afriend run /tmp/reviews/auth-review.md --repo /work/acme/service --mode report
```

- `--repo PATH` is optional. When omitted, the existing behavior is unchanged:
  the artifact's parent repository supplies code scope, and no repository
  means doc scope.
- When provided, `PATH` must resolve to the top level of a local Git worktree.
  Reject a file, a nonexistent path, a bare repository, a nested directory,
  and a path that is not a Git worktree. Do not silently climb or substitute a
  repository.
- `--repo` gives every repo-scoped friend the one explicit repository snapshot,
  even if the artifact is outside that worktree, is untracked, or is ignored.
  The artifact itself remains copied and hashed under the run directory; it is
  not inserted into the repository snapshot.
- A run with an explicit repository must record and render: artifact digest,
  explicit repository root, snapshot commit/tree, and that the artifact was
  independently frozen rather than bound to a commit blob. This remains true
  when the artifact happens to be ignored inside the selected worktree.
- `--resume` restores the saved repository identity and frozen artifact. It
  must reject `--repo` on resume rather than allowing an invocation to change
  repository authority. Existing in-repository runs retain their current
  resume validation.
- Loop iterations continue to freeze the live artifact text and resnapshot the
  explicit repository on an artifact revision change. The artifact digest and
  repository identity are both recorded for each revision.
- `afriend resolve` continues to validate evidence against the saved repository
  snapshot. It does not require an artifact path inside that repository.
- No new provider, sandbox, external-tool, network, or write authority is
  granted. Existing per-friend OS confinement and deny-by-default policies
  remain unchanged.

## Workstream 2: no-dispatch preflight (separate design task)

Before implementation, write and approve a design that answers these fixed
questions:

- Is the command `afriend run --dry-run`, `afriend preview`, or a host-only
  session prompt? Choose one; do not create aliases with divergent behavior.
- The output must be computed from the same roster, profile, provider policy,
  readiness, authority, scope, timeout, call, wall-clock, and loop settings as
  dispatch. It must clearly state it made no provider/model invocation.
- It must render: artifact, automatic/explicit/doc scope, selected repository
  if any, friends and advisory-host status, denied/allowed external tools,
  mode and rounds, maximum calls, wall-clock cap, timeout, and confirmation
  policy.
- It must be JSON-capable and stable enough for a host skill to quote before
  dispatch. It must not persist a run directory, create a worktree, contact an
  HTTP endpoint, or run a provider CLI capability probe.
- Existing noninteractive `afriend run` must remain noninteractive unless a
  future explicit confirmation flag is selected.

## Workstream 3: classified failure and retry policy (separate design task)

Before implementation, define a closed, provider-declared taxonomy. The first
version may classify only local process outcomes and existing HTTP readiness
results: unavailable executable, unavailable HTTP endpoint, startup failure,
timeout, signal termination, invalid output, and zero usable answers.

Rules:

- Never infer a DNS, authentication, rate-limit, or model failure from free
  text in provider stderr.
- Never add a generic “send a prompt to test reachability” probe.
- Allow retry only when an adapter declares a bounded, idempotent, non-billed
  readiness action. Missing declaration means no retry/probe.
- Persist a sanitized machine-readable failure class and render it in status,
  report, and terminal summaries. Preserve current exit-code precedence.
- Make retry count/backoff policy explicit, bounded, disabled by default, and
  immutable on resume.

## Workstream 4: distribution refresh UX (separate design task)

Before implementation, enumerate supported install surfaces: PyPI CLI,
Codex plugin projection, Claude marketplace/plugin projection, and source
checkout. The design must distinguish “a new version was published” from “a
host has refreshed its installed plugin.”

Deliverable options to choose between:

- A read-only `afriend doctor --updates` report that compares the installed CLI
  and plugin manifest versions with the current release metadata.
- Host-specific documented refresh commands emitted only when a host’s install
  location can be determined without touching it.
- A release checklist/workflow that validates the canonical asset projection,
  plugin manifests, and released distributions before publication.

Do not auto-edit a host's plugin cache or configuration, and do not claim that
PyPI installation upgrades a Codex or Claude plugin.
